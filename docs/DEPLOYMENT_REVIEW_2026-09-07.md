# Shipwrite 영어 자동화 점검·배포와 유입 개선 제안

점검일: 2026-09-07 KST. 영어 생성기 `Ahn-Hyun/ai_blog_gen`와 영어 사이트 `Ahn-Hyun/ai-blog-V1`만 대상이다.

## 이번에 확인하고 수정한 문제

- GitHub Actions가 `disabled_inactivity`였다. 재활성화했다.
- GitHub 변수의 옛 Gemini 모델이 코드 기본값을 덮어쓰고 있었다. Gemini 3.8 Flash / Gemini 3.1 Flash Image / GPT-5.5 high로 맞췄다.
- GitHub Secrets에 OpenAI 키가 없어 주간 작업이 Gemini로 대체 실행되고 있었다. 기존 로컬 OpenAI 키를 값 노출 없이 영어 Actions에 등록했다.
- 영어 생성기 GitHub 변수에 한국어 도메인·작성자와 허용되지 않는 기본 카테고리가 있었다. 영어 사이트 값으로 수정했다.
- 섹션 작성 실패를 건너뛰어 일부 내용만 발행할 수 있었다. 필수 섹션 실패·빈 응답·출력 토큰 한도 초과를 보류 처리한다.
- 검색·주제 선정 실패가 성공 종료될 수 있었다. 재시도 가능한 오류로 보고한다. 정상적인 시간대/중복 실행 건너뛰기는 유지한다.
- 근거 추출의 잘못된 인용/수치는 한 번 수정한 뒤 동일한 검사를 다시 받는다. 계속 실패한 항목은 제외하고, 남은 각 근거도 동일 검사를 통과해야 한다. 유효 근거가 없으면 발행을 보류한다. 작성기에는 검증된 주장만 사용하고 통계 모집단·기간을 보존하도록 명시했다.
- 최종 출처 검수가 지적한 문제를 본문 수정에 반영하는 단계를 연결했다. 한 번 수정한 뒤 Humanizer와 같은 최종 출처 검사를 다시 통과해야 저장한다. 검수 서비스 장애는 승인으로 취급하지 않고, 계속 거절되는 원고도 발행하지 않는다.
- 본문 이미지 설명 객체가 문자열로 변환되어 섹션 배치 정보가 사라졌다. 객체를 유지하도록 수정했다.
- 실패한 원고의 검수 기록이 Actions 종료와 함께 사라졌다. 거절 기록을 14일 보관하는 아티팩트를 추가했다.
- 파일 수정시각과 상태 파일을 비교하던 새 글 감지는 신뢰할 수 없어 Git 변경 목록으로 대체했다.
- 수집 글자 수 예산을 소진한 뒤에도 나머지 URL에 추출 API를 호출하던 낭비를 없앴다.
- 한 원고가 보류되면 이미 최종 검수·빌드를 통과한 다른 원고까지 발행되지 않던 배치 처리 문제를 수정했다. 검증된 `draft: false` MDX와 그 원고의 이미지, 발행 상태만 스테이징한다. 보류 초안과 소속 원고가 없는 이미지는 제외한다. 보류가 남으면 Actions 실행은 실패로 표시해 재시도 대상을 숨기지 않는다.
- 날짜가 있는 Google News 중계 링크만 남기고 원문 후보를 버리는 검색 오류를 실제 실행에서 확인했다. 날짜순 우선순위는 유지하면서 원문 후보도 남긴다. 검색 요약문을 실제 가져온 본문으로 대체 사용하던 경로도 제거했다.
- 평가 캐시 지문에 GPT reasoning effort가 빠져 있었다. 추가했다.
- About 페이지가 확인되지 않은 금융 전문가 경력을 주장했다. 실제 AI 자동화 방식과 검수 한계로 수정했다.
- Cloudflare Pages에 `VIEW_COUNTERS` 연결이 없었다. 기존 `us.ship-write` KV를 운영 환경에 연결했다. 별도 검증 키에서 POST 1 → GET 1 확인 후 검증 키를 삭제했다.

## 유입을 늘리기 위한 다음 작업

운영 측정은 워크플로 상태와 별도로 마지막 정상 발행일, 시도/승인/보류 건수, 보류 단계·원인, 배포 성공 여부를 남기는 것이 좋다. 실제로 장기 미활동 비활성화와 '성공인데 새 글 없음'이 있었으므로 이 둘을 감지해야 한다. 이번에는 재활성화와 오류 보고를 복구했으며, 별도의 외부 감시 작업은 생성하지 않았다.

현재 구조는 날짜별 뉴스에서 새 글을 만드는 데 집중한다. 동일한 질문에 답하는 기존 페이지가 있는지 판단하거나 검색 성과를 다음 편집 결정에 반영하는 단계가 없다. 점검 시 영어 MDX 62개 본문의 다른 블로그 글 링크는 0개였다. 헤더·카테고리·태그 탐색 링크와는 별도 집계다.

기존 글의 정정 검토도 필요하다. 5월 24일 데이터센터 글의 `guaranteed cash flows`, 5월 25일 Fed·기술주 글의 `removing the tail risk` 같은 단정이 기존 발행 본문에 남아 있다. 새 생성기 배포가 과거 62개 글을 소급 검수하거나 수정하지는 않는다. 해당 글들은 추가 유입을 유도하기 전에 원문 대조와 정정을 우선할 후보로 둔다.

### 1. 검색 성과를 편집 작업 목록으로 연결

Search Console에서 페이지·검색어·국가·기기별 노출, 클릭, CTR, 평균 순위를 수집한다. 우선 28일과 이전 28일을 비교하되, 작은 표본의 CTR 변화나 평균 순위만으로 성공을 단정하지 않는다. 검색어 정보는 일부만 제공될 수 있다.

- 노출은 있지만 클릭이 적은 페이지: 실제 검색어 의도와 제목·도입부가 맞는지 검토.
- 순위 8~20 부근의 관련 페이지: 빠진 답, 데이터 갱신, 내부 링크를 우선 검토하는 초기 규칙. 보편적인 정답이나 상승 보장은 아니다.
- 같은 질문으로 여러 글이 노출되는 경우: 기존 글 갱신/통합 후보로 만들고 URL 변경은 리디렉션 계획과 함께 별도 검토.
- 성공 기준: 영어/미국 타깃의 유기 검색 클릭, 읽기·다음 글 이동, 재방문·구독을 구분한다. KV 조회수는 사람 수나 순방문자가 아니다.

[Search Console API 문서](https://developers.google.com/webmaster-tools/v1/searchanalytics/query)

### 2. 새 글 작성 전에 기존 글 갱신 여부 판단

`독자 질문 → 관련 기존 글 검색 → 갱신 또는 새 글 결정 → 근거 수집 → 작성/검수` 순서를 추가한다. 날짜와 제목 문자열이 다른 것만으로 새로운 독자 질문이라고 판단하지 않는다. 실질적 변경 없이 게시일만 최신으로 바꾸지 않는다.

초기 실험은 매일 두 글을 무조건 추가하는 대신 한 주에 핵심 질문 해설 1편, 공식 데이터 갱신 1편, 기존 글 개선 1편 정도로 작게 운영할 수 있다. 이는 권장 실험안이며 이번에 발행 일정을 바꾸지는 않았다.

### 3. 독자 질문별 중심 글과 문맥상 내부 링크

넓은 금융 뉴스 경쟁보다 기존 글과 연결되는 좁은 질문부터 검증한다. 예시는 검색량을 확인한 키워드가 아니다.

- Why can mortgage rates stay high after a Fed cut?
- What does data center cost per MW exclude?
- How do interest rates change REIT refinancing costs?

핵심 설명 페이지에서 세부 사례로, 새 사례에서 핵심 설명으로 문맥에 맞는 링크를 연결한다. 이미 발행된 실제 URL만 허용하고 자기 링크·깨진 링크·주제 무관 링크를 막는다. 링크 개수 할당보다 독자에게 필요한 다음 질문을 우선한다.

[Google 내부 링크 가이드](https://developers.google.com/search/docs/crawling-indexing/links-crawlable)

### 4. 원문 요약 이상의 재사용 가능한 자료

공식 통계의 단위·관측일·개정 이력을 보존한 차트/표, 가정이 명확한 계산 예시, 한 질문에 대한 비교표를 제공한다. 계산은 Python/TypeScript의 결정적 로직이 하고 AI는 설명한다. 출처에 없는 수치·가짜 현장 경험·검증되지 않은 전문가 경력은 추가하지 않는다.

금융 주제에서는 문체보다 출처, 저자/제작 방식, 오류 수정 경로, 불확실성의 명확성이 먼저다. 사람처럼 보이는 글보다 사람이 질문을 해결할 수 있는 글을 목표로 한다.

[Google의 유용하고 신뢰할 수 있는 콘텐츠 기준](https://developers.google.com/search/docs/fundamentals/creating-helpful-content)

### 5. Humanizer/Promptfoo를 운영 판단에 활용

Humanizer는 편집 단계이며 유입 최적화 도구가 아니다. 과도한 축약, 근거 누락, 수치 범위 변경 사례를 고정 평가에 넣고 새 모델·프롬프트 적용 전에 회귀를 확인한다. 최종 검수 실패 원고는 발행하지 않는다. 주간 소량 원고를 직접 읽어 자동 평가의 오탐/미탐도 기록한다.

Promptfoo 점수와 실제 검색 클릭을 구분한다. 제목 변경 실험은 같은 페이지에 여러 변경을 동시에 넣기보다 변경일과 내용을 기록해 후속 성과를 비교한다. 검색 변동과 계절성 때문에 단순 전후 차이는 인과효과가 아니다.

### 6. 재방문 경로

RSS와 기존 문의 경로를 활용하고, 운영 여력이 생기면 좁은 주제의 주간 요약 구독을 검토한다. 외부 커뮤니티에는 해당 질문을 해결하는 설명과 출처를 제공하는 방식이 적합하다. 자동 대량 홍보·댓글·메일 발송은 이번 작업에 포함하지 않는다.

## 권장 첫 구현

**Search Console 성과를 기존 글 개선 후보로 만드는 주간 작업 목록 + 기존 페이지를 찾는 주제 중복 검사**부터 시작한다. 데이터 접근을 확보한 다음 내부 링크와 기존 글 갱신을 연결하면, 새 모델 추가보다 개선 결과를 측정하기 쉽다.
